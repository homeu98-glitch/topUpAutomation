## 修復 Vercel Hobby 12 Serverless Function limit
- 問題：Vercel 部署讀 `api/` 目錄，每個有 `export default` 嘅檔自動變成一個 function。`api/` 入面有 35 個 route handler + index.js → ≈36 function，爆 Hobby 上限 12。之前嘅 `server.js` Express 單體根本冇被 Vercel 用（有 `api/` 喺度就行 Serverless Functions mode，ignore root server.js）。
- 解法：將 35 個 route handler 由 `api/` 搬去 root `routes/`（保留 tree，內部 `../lib`/`../../lib` 相對路徑深度唔變）。`api/` 只留 `index.js` 做單一 catch-all function。
- import 路徑改動：`server.js` → `./routes/...`；`api/index.js` 動態 import → `../routes/...`；`public/*.js` 嘅 `/api/...` HTTP 路徑唔使改（catch-all 照 handle）。
- `vercel.json` 個 cron `/api/cron/auto-approve` 經 catch-all 處理，唔受影响。
- 結果：Vercel 只會部署 1 個 function（≤12）。`node --check` 兩個 entry 檔都 pass。
- 注意：Hobby 嘅「單次部署最多 12 function」硬上限至今未改（2025-2026 改嘅係 CPU/記憶體/呼叫次數計費模型，唔係 function 數量上限）。

## 補鑊：catch-all 改用 bodyParser:false 引起嘅 SSO 回歸
- 徵狀：deploy 新版本後，由 ledger（澳門會員通）iframe 入去彈「請從澳門會員通進入」。原因：前端 `app.js` 由 URL 抽 `ssoToken` → POST `/api/auth/sso-login`；`routes/auth/sso-login.js` 靠 `req.body` 收 token（Vercel 舊制下獨立 function auto-parse JSON）。改做單一 catch-all `api/index.js` 後，個 catch-all 聲明咗 `bodyParser: false`，所有經佢嘅 JSON POST route 都收唔到 `req.body` → `sso-login` 回 400「缺少 SSO token」→ 前端當登入失敗彈 gate。
- 修法：`api/index.js` 保留 `bodyParser: false`（保護 3 個 multipart route：analyze / customer/submit / customer/submit-raw，要用 formidable 讀 raw stream），另加 `readJsonBody(req)` 喺 catch-all 開頭手動 parse `application/json`（跳過 GET/HEAD/OPTIONS 同 multipart）。咁 JSON route 同舊制行為一致，multipart 唔受影響。`node --check` 通過。
- 教訓：任何 route 由「獨立 function（各自 bodyParser 設定）」合併成「單一 catch-all」時，必須喺 catch-all 層重現 body parsing 行為，否則所有靠 `req.body` 嘅 POST 會死。

## 診斷 /api/analyze 嘅 401 Missing Authentication header
- 用戶由 ledger 入去，AI 辨識報 `401 {"error":{"message":"Missing Authentication header","code":401}}`。
- 直接 curl OpenRouter 驗證錯誤語義：
  - `openrouter.ai/chat/completions`（無 /api/v1）→ 返 HTML 404 page（唔係 JSON 401），證明部署個 `AI_BASE_URL` 正確有 `/api/v1`，請求確實去到 OpenRouter API。
  - `/api/v1` 無 auth header → `No cookie auth credentials found`（唔同 message）。
  - `/api/v1` ＋ **bogus Bearer key** → 正正係 `Missing Authentication header` —— 即 OpenRouter 對「無效 key」同「冇 header」都報同一句。所以 401 唔等於 key 冇set，而係 key 被拒。
- 部署後 `/api/health` 新增診斷欄位（唔洩露 key，只顯示格式）證實實際 config：
  - `AI_BASE_URL=https://openrouter.ai/api/v1` ✅、`AI_MODEL=google/gemma-3-12b-it:free` ✅（呢個 free Gemma 就係「平D方法」）。
  - **`AI_API_KEY` 格式 = `other`（唔係 `sk-or-`、唔係 `AIza`）→ 無效 OpenRouter key，係 401 真正元兇**。用戶要去 openrouter.ai/keys 開 `sk-or-...` key。
  - `AI_OCR_MODEL=qwen-vl-ocr`、`AI_TEXT_MODEL=qwen-plus-2025-07-28`、`AI_VL_FALLBACK_MODEL=qwen3-vl-32b-instruct` 全部係 Aliyun model，OpenRouter 無 → key 修好後呢三個會即刻 404/model-not-found，必須一併改做 OpenRouter 有嘅 model（例：google/gemini-2.5-flash 或 google/gemma-3-12b-it:free）。
- 改咗 code：① `api/index.js` `/health` 加 `aiBaseUrlEndsWithApiV1` / `aiKeyFormat` / 四個 model 名（只顯示格式唔顯示 secret）；② `lib/topup-service.js` `requestChatCompletion` 嘅 401/404 error 加中文提示；③ `getHealthPayload()` 同步。commit `29dab85` 已 push + 部署。
